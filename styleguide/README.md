# evoland-plus style guide

How code and prose in this repository should look, and why.
It is written for both human contributors and coding agents: every rule is short enough to apply mechanically, and the reasoning is given where a rule is not self-evident.

| Writing...                                  | Read                   |
| ------------------------------------------- | ---------------------- |
| R code in `R/`, tests in `inst/tinytest/`   | [r.md](r.md)           |
| C++ in `src/`                               | [cpp.md](cpp.md)       |
| SQL in `inst/*.sql` or inline in R          | [sql.md](sql.md)       |
| Vignettes, roxygen text, comments, commits  | [prose.md](prose.md)   |

## Precedence

1. What the formatter or linter produces wins over anything written here. Don't fight the tools; change their configuration if a rule needs to change.
2. This guide wins over the existing code. Much of the code predates the guide; when you touch a function, bring what you touch into line, but don't reformat or rewrite unrelated code in the same change.
3. Where this guide is silent, follow the surrounding code. Where the surrounding code is inconsistent, follow the [tidyverse style guide](https://style.tidyverse.org/) for R and the [LLVM style](https://llvm.org/docs/CodingStandards.html) for C++.

## Tooling

| Language   | Formatter                                                 | Config                | Linter                       |
| ---------- | --------------------------------------------------------- | --------------------- | ---------------------------- |
| R          | [air](https://posit-dev.github.io/air/) (`air format .`)  | `air.toml`            | lintr (`.lintr`)             |
| C++        | clang-format (`git clang-format` on changed lines)        | `.clang-format`       | clang-tidy via `.clangd`     |
| SQL        | [sql-formatter](https://github.com/sql-formatter-org/sql-formatter) | `.sql-formatter.json` | none                         |
| Quarto     | none; see [prose.md](prose.md)                            |                       |                              |

CI suggests air formatting on pull requests (`.github/workflows/format-suggest.yaml`).
The other formatters are not enforced in CI; run them on the files you change.
Never format `R/RcppExports.R` or `src/RcppExports.cpp`: they are generated by `Rcpp::compileAttributes()`.

## What goes where

The documentation follows [Diátaxis](https://diataxis.fr/):

- **Tutorials** (learning by doing a full analysis) and **how-to guides** (a recipe for a known goal) are vignettes in `vignettes/*.qmd`.
- **Reference** is roxygen documentation in `R/`, rendered to `man/` and the [pkgdown site](https://ethzplus.github.io/evoland-plus/).
- **Explanation** (design rationale, why the database looks the way it does) currently lives in the [GitHub wiki](https://github.com/ethzplus/evoland-plus/wiki). Parts of it describe the earlier `parquet_db` design; treat the code as authoritative where they disagree.
- **Conventions** (this guide) and agent instructions (`AGENTS.md`) live in the repository, so that they are versioned with the code they describe.
